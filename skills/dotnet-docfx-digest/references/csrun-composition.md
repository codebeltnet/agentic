# Standalone and repository-backed runtime evidence

Choose the easiest faithful reproduction before authoring. Prefer standalone csrun. For an intrinsic application/test assembly boundary, DocFX owns a separate pinned repository-backed one-shot command: download to OS temp, run the maintained targeted test, verify positive execution of that exact test, and clean source/build artifacts. Offer an independent official SDK Docker equivalent where practical, without requiring a host SDK. See [one-shot examples](one-shot-examples.md) for the verified ManagedApplicationFixture regression and artifact generator. This is execution of trusted repository code and its original project graph, not isolated manifest execution. csrun owns only standalone execution; neither engine nor schema v1 changes.

Keep the existing DocFX inventory and source discovery. This skill owns public API discovery, namespace/type pages, UID/overwrite placement, source-backed explanation, project-aware sample compilation and documentation completion. `dotnet-csrun` owns compatible standalone construction, real xUnit v3 execution, native/Docker deliverables, behavioral verification, localized corrections and execution evidence. Apply both skills in the parent context when authorized; deterministic validators never launch another skill, agent, or authenticated model.

Use `create` for a new complete standalone example; `verify` to inspect/execute unchanged source; `repair` for a relevant correction authorized by the documentation task; and scoped `audit` for classification and runtime evidence. Read the installed csrun skill's lifecycle and feasibility references. Apply the [example design contract and execution classification](example-architecture.md) before source generation. Preserve contextualized partial excerpts and project boundaries; neither existing nor new excerpts are standalone executables merely because they contain C#.

Add standalone feasibility, exact source/manifest identities, exact published package pins, expected observations, and separate native/Docker statuses and evidence paths to the existing example inventory when useful. Keep evidence and generated wrappers in a temporary/ignored workspace. Reuse only current matching evidence under the requested verification policy. Runtime and compilation claims remain separate: a project-backed sample may compile without being independently runnable, and a csrun run against a release does not prove the unpublished checkout.

Retain repository-aware validation for unpublished assemblies, project references, separate application/test assemblies, full hosts/HTTP pipelines and unavailable infrastructure. In particular, application-owned `Main` plus `ApplicationTest` must keep its real composition root and separate application identity; removing Main or registering the same service in a different host is not an equivalent correction. Use the existing project/test workflow. Do not add a competing compiler, manifest format, or project scaffolding for csrun compatibility.

For an executable example, choose an allowed `// Program.cs` form or bind the genuine test source to its maintained project context. A standalone xUnit v3 test can be executed by csrun; a test requiring a separate application assembly belongs in the actual project/test graph. A class-library fence with no executed operation supports a compilation claim only. If a separate harness invokes it, disclose and identify both sources; do not claim byte identity.

Whenever a runnable example is delivered, surface both complete Native and Docker execution options together unless one transport is genuinely unsupported. In a direct Codex response, include each as an independently copyable and executable script; never extract `## Native` alone when the corresponding `## Docker` option exists, point only to a reference/generated file, or require manual assembly. Track verification separately per transport: report `Verified`, `Failed`, `Unverified`, or `Unsupported` only from that transport's own execution or support evidence. For generated DocFX websites, associate both assets with the same C# sample so its Native and Docker copy controls appear together.

Use one canonical source for the visible fence and standalone manifest. Compare after newline normalization. For a related repository test, identify its pinned source and state which behavior it verifies.
