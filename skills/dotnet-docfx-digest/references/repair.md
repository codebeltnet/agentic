# Repair existing documentation and verify behavior

## Assemble the packet queue

Before editing, materialize the machine-readable behavioral review ledger in temporary/session storage with `docfx.cs --repo-root <root> --operation <repair|repair-csrun> --init-behavioral-ledger <temp-ledger> --json` (adding explicit scope flags only when the user restricted scope). The tooling enumerates every in-scope example from the authoritative inventory — including untouched pages with zero deterministic diagnostics, passing compilation or cached transport logs — and tags `changedPriority` without narrowing a repository-wide invocation. Key work by project, UID, page and fence ordinal. For every selected packet take the union of:

- Current validator diagnostics, including follow-on diagnostics after structural fixes.
- Documentation, sample, API or dependency changes since the task's base (for a PR use its merge base with the target branch), plus staged, unstaged and untracked work. Inspect the previous scenario before converting it.
- Every supplied review finding. Map each finding to its affected fence, including duplicates. Record repaired, already resolved or inapplicable with concrete evidence, or unresolved.
- Every in-scope example lacking a current passing behavioral comparison. Enumerate existing fences from the materialized ledger, including untouched files. A compile result, timestamp or previous transport pass alone supplies no comparison.

Deduplicate inspections, retaining all reasons and finding identities. Prioritize `changedPriority` entries within packets without dropping untouched examples. A missing baseline or empty diff still leaves the inventory and findings available. Reuse existing execution logs (such as `.docfx-run-verification` captures) only when `sourceSha256`, `claimSha256`, `dependencySha256`, `recipeSha256` and `executionTopology` still match the current example; recheck changed prose even when the script hash is identical.

## Check one example

1. Read the lead, fence, output comments and associated recipe. Name the documented operation, consumer scenario, inputs and observable result. Derive the expected result for this version and overload from its implementation, public contract, relevant tests and maintained usage. Record concrete source paths. For variable data use a stable property or relationship.
2. Trace from the actual entry point. Check every promised branch runs, loops have the correct nesting and counts, and state is observed while valid. Follow data from the call through to the returned object, response, stream, emitted event or assertion. Would the example still appear successful if the documented operation were removed? If yes, inspect what the output actually measures.
3. Execute the existing example where supported using its established topology, or inspect a current matching runtime log whose provenance and hashes still match. Compare values, cardinality, order and labels against the expectation. A middleware header comes from the response after the request traverses the pipeline. Authentication evidence comes from exercising the handler. Options, inputs, exit code 0 and cached transport status alone cannot show these effects.
4. Correct the smallest part that restores the consumer scenario. Preserve required host/runner and assembly boundaries. Exercise missing operations before considering a prose change. Correct inaccurate labels or expected results from evidence. Check acquisition, ownership, disposal, formatting and indentation in the rendered fence. Keep a console demonstration concise; use a test runner when it is part of the scenario.
5. Re-execute modified examples and update the ledger entry with `documentedOperation`, `consumerScenario`, `authoritativeEvidence`, `expectedObservation`, `actualObservation`, `observationEvidencePath` (or `executionCommand`), `disposition` (`verified-behavior`, `source-reviewed-only` for non-executable/project-bound topologies, `unresolved-finding` or `unavailable-execution`), `transportStatus` and `findings`, refreshing hashes when code, claims, dependencies or recipes changed. For composed `repair csrun`, regenerate affected recipes/assets and verify each applicable transport independently. Keep already-correct source intact. Reconcile the completed ledger through `docfx.cs --repo-root <root> --operation <repair|repair-csrun> --behavioral-ledger <temp-ledger> --build-api-model --validate-samples --verify-docfx-build --json` before claiming completion.
