# Architecture regression evidence

These are maintained regression fixtures, not a new project generator. Tests copy them to OS temp before building; never build this tree in place.

The split InventoryWorker scenario adapts the [published example](https://xunit.codebelt.net/api/Codebelt.Extensions.Xunit.Hosting.ManagedApplicationFixture-1.html). Its assembly contract is verified against the implementation and worker functional tests at [codebeltnet/xunit 84b13767cb9484f8f3a36a71875662edfdb3e511](https://github.com/codebeltnet/xunit/tree/84b13767cb9484f8f3a36a71875662edfdb3e511), detailed in [example architecture](../../../references/example-architecture.md). Runtime tests use the real published `Codebelt.Extensions.Xunit.Hosting` 13.0.0 and xUnit v3 4.0.3 packages, not substitute fixtures or simulated assertions. The app uses the SDK's ASP.NET Core shared framework for hosting references; that fixture dependency does not imply all hosting consumers require ASP.NET Core.

The test asserts the application registration's value, invocation of the real Main, and different application/test assemblies. Its assertion performs no service registration. Compiling the merged source as a library would conceal the executable topology; compiling it as an xUnit executable must fail with CS0017. Removing Main must not make the documentation acceptable. Runtime negative controls remove the application's registration (the original assertion must fail), then supply that registration in the test's ConfigureHost override (the assertion can pass despite the missing application registration). The latter is evidence of a changed contract, not a recommended correction.

Architecture-sensitive editorial acceptance cases are also versioned in `evals/evals.json`. Static checks cannot prove prose truth: a test-owned registration may be valid for an override scenario but cannot demonstrate original application registration; a compiling middleware example may still place authentication after authorization; and a successful build is not observed runtime success. Review those contracts against the linked implementation/tests and execution evidence.
