# Feasibility and semantic recovery

Understand intent → Inspect source → Assess feasibility → Choose execution path → Construct manifest → Execute → Verify → Repair or explain limitation → Deliver evidence. Use source and authoritative implementation evidence, not a homegrown C# parser. Pattern matches are warning signals, never complete semantic analysis.

| Outcome | Decision before execution |
| --- | --- |
| Compatible | Complete console program with one entry point, or self-contained public xUnit v3 tests whose dependencies fit the manifest. Execute directly. A test may construct and dispose its own host/DI container when that is the behavior requested. |
| Adaptable | Explain a transformation and why it preserves the requested observation, dependencies, lifecycle and assembly identity assumptions. For example, adding a missing import to an otherwise complete fact preserves its assertion. Execute and publish the adapted source with the change disclosed. |
| Unsupported | Essential separate project outputs/references, independently compiled application entrypoint assembly, or build customization unavailable in manifest v1. Preserve the original source; explain and recommend the appropriate project workflow. |
| Undetermined | Inspect missing source, fixture implementation, package docs and project structure. If still inconclusive, execution can supply evidence; update the assessment from diagnostics without guessing a repair. |

Inspect candidate entry points in test mode, including explicit `Main` methods and top-level statements. Explicit methods can conflict with the generated xUnit entry point (CS0017); top-level code can take precedence and bypass the runner instead. A successful build or exit zero then proves no tests. Do not assume every method named Main is an entry point, or every hosting fixture requires separate assemblies. Establish the actual fixture contract. Console applications can legitimately use an explicit Main or top-level statements; multiple executable candidates require inspection too.

External project references, unpublished local implementations and multiple project outputs cannot be supplied through `dependsOn`, which resolves published NuGet packages. Platform-specific frameworks require a suitable environment; they are not automatically source defects. Tests using databases, network services or other external infrastructure need those prerequisites and must disclose their scope; missing services may be an environment issue rather than a manifest limitation. Do not silently replace local code with a published version, retarget a framework, or substitute a fake service and retain the original verification claim.

## Why the InventoryWorker regression needs project boundaries

Inspected on 2026-11-16: released [csrun v0.2.1 Write-TestProject](https://github.com/codebeltnet/csrun/blob/v0.2.1/csrun.ps1) emits one `Sample.csproj` with `OutputType=Exe`, `UseMicrosoftTestingPlatformRunner=true`, package/framework references and the entire source in `Sample.cs`. It supplies no application project/reference or startup-object control. [xUnit v3 package documentation](https://xunit.net/docs/nuget-packages-v3) describes injection of the executable runner entry point; the inspected [entrypoint generator](https://github.com/xunit/xunit/blob/1b174815ca54707854077b027365188384687cf3/src/xunit.v3.msbuildtasks/XunitEntryPointGenerator.cs) emits Main calling TestPlatformTestFramework.RunAsync for MTP, and its [targets](https://github.com/xunit/xunit/blob/1b174815ca54707854077b027365188384687cf3/src/xunit.v3.core/Package/buildTransitive/xunit.v3.core.targets) attach generated source before compilation. Therefore `WorkerProgram.Main` in the same test source competes with that runner, producing CS0017 before discovery.

The deeper issue is assembly identity. At Codebelt xunit revision `84b13767cb9484f8f3a36a71875662edfdb3e511`, [ApplicationTest](https://github.com/codebeltnet/xunit/blob/84b13767cb9484f8f3a36a71875662edfdb3e511/src/Codebelt.Extensions.Xunit.Hosting/ApplicationTest.cs) initializes the fixture and exposes its host. [ManagedApplicationFixture](https://github.com/codebeltnet/xunit/blob/84b13767cb9484f8f3a36a71875662edfdb3e511/src/Codebelt.Extensions.Xunit.Hosting/ManagedApplicationFixture.cs) passes `typeof(TEntryPoint).Assembly` to [DeferredHostFactory](https://github.com/codebeltnet/xunit/blob/84b13767cb9484f8f3a36a71875662edfdb3e511/src/Codebelt.Extensions.Xunit.Hosting/Internal/DeferredHostFactory.cs). Its [ProgramHostFactoryResolver](https://github.com/codebeltnet/xunit/blob/84b13767cb9484f8f3a36a71875662edfdb3e511/src/Codebelt.Extensions.Xunit.Hosting/Internal/ProgramHostFactoryResolver.cs) resolves `assembly.EntryPoint`, invokes it and captures hosting diagnostics. The [hosting documentation](https://github.com/codebeltnet/xunit/blob/84b13767cb9484f8f3a36a71875662edfdb3e511/.nuget/Codebelt.Extensions.Xunit.Hosting/README.md) explicitly describes application-owned Main startup. TEntryPoint is a type in the application assembly, not a request to invoke a method on that type by name.

The submitted `Host_ContainsApplicationService` must prove that the actual application's composition root registers `WorkerIdentity`. Deleting or renaming Main cannot preserve that claim: the fixture still resolves the test executable's assembly entry point. Forcing the runner startup object does not create an independent application assembly; forcing the application startup bypasses the runner. Removing the fixture or independently registering the identity in a new host tests different behavior. Keep the exact original regression in `evals/files/inventory-worker.json`; do not replace it with a reduced passing test.

## Recovery and reporting

Classify the cause before editing: (A) example-owned syntax/import/API/package defect: correct only with evidence and preserve intent, then rerun; (B) environment: preserve source and target, identify SDK/runtime/platform/network/Docker/service prerequisites and select an authorized compatible environment; (C) execution-model limitation: explain the missing capability without source mutation; (D) insufficient evidence: investigate implementation/docs before concluding unsupported or inventing APIs.

For the InventoryWorker preflight report: **Feasibility: Unsupported by current csrun manifest. Verification: Unverified. Reason: required executable/application assembly separation is unavailable. Recommendation: verify the real application with normal application/test project separation.** If execution was attempted, report **Failed**, CS0017, nonzero exit and no discovered/executed tests; this establishes execution incompatibility, not application correctness or an assertion failure.

Recommend `dotnet-test` for establishing/preserving entrypoint-owned repository testing infrastructure, or `dotnet-remote-testing` for executing an existing repository test workload in a container. Describe these as separate workflows; never silently switch engines or claim csrun executed the original test. A standalone host/DI fact can be offered as a **reduced demonstration** of registration/resolution only; it does not verify WorkerProgram startup. Prefer a concise diagnosis and recovery path over a known-failing Copy & Run block.

For documentation, use `dotnet-docfx-digest`'s `references/one-shot-examples.md`: a pinned snapshot of the maintained repository can execute the original targeted test with its original project graph in one copy/paste block. Verify the precise test identity and positive executed/passed counts with the actual MTP/xUnit v3 conventions. Report native and Docker evidence independently. This separate repository-backed strategy does not expand csrun or make the source manifest-compatible. If unavailable, preserve the concise illustration, explain prerequisites and the standalone limitation, link implementation/example/test/project, and label execution unverified. Source links are a fallback, not a replacement for an available working command.
